# RepoPalette 产品决策

更新日期：2026-08-12

## 1. 产品定位

RepoPalette 将 GitHub 公开仓库汇总为一张可配置、定期更新的编程语言构成图。

它不是编程水平评分器，也不是 AI 代码检测器。首要价值是把分散在多个仓库中的语言统计整理成清晰、可核对、适合放入 Profile README 的 SVG 图表。

## 2. GitHub 仓库与 Marketplace 主文案

### 首页主文案

> **比标准语言卡更有辨识度，比综合统计框架更简单。**

RepoPalette 专注 GitHub 编程语言构成。只需选择布局和主题，即可基于范围可核对的公开仓库统计，生成一张保存在自己 Profile 仓库中的 SVG 语言图。

主按钮：`开始配置`

辅助按钮：`使用 AI 协助安装`

### 支撑差异化的四项产品能力

#### 有辨识度的默认设计

`orbit`、`constellation` 和重新设计的 `bars` 不是给标准图表简单换色，而是围绕 GitHub 语言构成重新组织信息层级；同时保留语言名称和准确占比，不以牺牲可读性换取视觉效果。

#### 两个核心选项即可使用

普通用户只需选择 `style` 和 `theme`。排除仓库、颜色、尺寸、动效和编程方式分组都放在高级配置中，不要求用户先理解一个庞大的插件系统。

#### 统计范围可以核对

明确说明纳入和排除哪些仓库，并同时输出审计 JSON。仓库或语言分页不会静默截断；数据异常时停止更新，而不是用残缺结果替换现有图表。

#### 输出由用户自己保存

生成结果提交到用户自己的 Profile 仓库。即使某次更新失败，README 仍可显示上一份有效结果，不依赖每次访问时调用外部绘图服务。

### 为什么不用最常见的方案

如果用户只想最快贴一张普通语言排行图，常见的在线卡片服务通常更省一步，RepoPalette 不应假装在这个场景里更简单。

Marketplace 中已经存在几类成熟选择。RepoPalette 的位置不是宣称每项能力都是首创，而是把“有辨识度、低配置、可核对、自有输出”组合成默认体验：

| 选择 | 最适合的需求 | 用户接受的取舍 |
| --- | --- | --- |
| 普通在线 Top Languages 卡片 | 最快嵌入一张熟悉的语言排行图 | 视觉通常较标准；显示时依赖实时图片服务 |
| [`Metrics embed`](https://github.com/marketplace/actions/metrics-embed) 等综合框架 | 在一套系统中展示大量 GitHub 指标 | 功能和配置项很多，需要投入时间选择插件与参数 |
| [`GitHub-Profile-Summary-Cards`](https://github.com/marketplace/actions/github-profile-summary-cards) | 一次生成多张成熟的 Profile 统计卡 | 输出类型预先定义，重点不是独立的语言视觉产品 |
| [`Repography`](https://github.com/marketplace/repography) 等托管 App | 安装式体验、在线仪表盘和私有仓库服务 | 依赖托管后端，并进入账户、隐私和订阅体系 |
| **RepoPalette** | 用很少配置生成有辨识度、可核对的语言构成图 | 需要在 Profile 仓库安装一次 Action；产品有意只专注语言构成 |

因此对外差异化应概括为：

> **更有辨识度的语言图，不以复杂配置和实时托管依赖为代价。**

支撑句：

> **一个布局、一个主题，生成一张统计可核对、文件归自己的 GitHub 语言图。**

一句更直接的选择建议：

> 只想最快嵌入一张标准语言排行图，现成服务已经足够；需要比标准卡片更有辨识度，又不想维护复杂统计系统时，选择 RepoPalette。

### Marketplace 短描述候选

> Distinctive GitHub language visuals, without configuration overload.

详细介绍再补充：只需 `style` 与 `theme` 两个核心选项；统计范围附带可核对数据；SVG 输出保存在用户自己的仓库。

### 差异化文案的发布门槛

这套表述只有在以下能力同时交付后才能用于正式发布，避免文案跑在产品前面：

1. 默认安装确实只要求用户决定 `style` 和 `theme`，其余参数都有合理默认值；
2. `orbit` 与 `constellation` 在盲看时能明显区别于常见横条、donut 和 pie 卡片；
3. 每次输出都包含仓库数量、纳入范围和语言统计的可核对 JSON；
4. SVG 确实提交到用户仓库，生成失败时保留上一份有效结果；
5. README 能用一个简短对比示例证明差异，而不是只靠形容词声称“更好看”或“更简单”。

### 不同渠道的语气边界

- **GitHub README / Marketplace：** 使用“编程语言构成图”“语言分布”“SVG 图表”等准确表达，不使用“长大”“代码成分卡”或会暗示复杂人格报告的措辞。
- **文档与安装页：** 保持简洁友好，但明确输入、输出、更新方式和统计范围。
- **社交媒体：** 可以偶尔使用“看看你的代码成分”等更轻松的说法，但不能让用户误以为当前产品会生成角色、故事或完整年度报告。

### 不应作为首页主卖点的技术词

以下内容应放在“为什么可信”或 FAQ，而不是首页第一屏：

- GraphQL pagination；
- PAT / `GITHUB_TOKEN`；
- 原子替换；
- 静态 SVG；
- 重试与审计 JSON。

它们负责证明产品可靠，但不是初学者开始使用产品的理由。

## 3. 统计边界

默认范围：

- 公开仓库；
- 用户本人拥有；
- 排除 fork；
- 默认排除 archived，可配置纳入；
- 支持排除指定仓库和语言。

“完整统计”的准确含义是：在上述范围内持续翻页取完，不静默截断；若数据异常则失败并保留上一份有效输出。

私有仓库、组织内非本人拥有的仓库、gist 和其他 Git 平台不属于默认承诺。

## 4. RepoPalette 的 Marketplace 形态

首发形态确定为 **GitHub Action**，不是 GitHub App。

理由：

- 任务是按计划或手动触发，而不是持续在线监听所有 webhook；
- 需要在 runner 上生成、校验并提交 SVG/JSON；
- 输出保存在用户仓库；
- 无需维护持续运行的服务器、数据库、登录系统和隐私后台；
- 独立 Action 仓库可以通过 `uses: onovich/RepoPalette@v1` 被复用。

只有在未来需要以下能力时，才重新评估 GitHub App：

- 安装后无需用户创建 workflow；
- 一个安装统一管理多个仓库或组织；
- 近实时响应仓库事件；
- 托管历史数据、跨仓库仪表板或付费方案；
- 访问内置 `GITHUB_TOKEN` 无法覆盖的资源。

## 5. 编程方式分组：用户自报，不做检测

### 产品原则

1. 不扫描代码并猜测哪些内容由 AI 生成。
2. 默认完全不区分，也不询问用户是否使用 vibe coding。
3. 只有用户主动打开高级选项时，才按用户自己的声明进行分组。
4. 该功能表达的是用户定义的“编程方式”，不是经过验证的代码作者身份。

### 首版分类

内部使用中性枚举：

- `vibe`：用户认为该语言属于全 vibe coding；
- `classic`：用户认为该语言属于传统/古法编程；
- `unclassified`：开启分组后仍未标记的语言。

界面文案可允许用户自定义，例如把 `classic` 显示成“古法编程”“手写为主”或其他称呼。

### 建议配置

默认关闭：

```yaml
with:
  style: orbit
  theme: aurora
  coding-style: off
```

用户主动启用：

```yaml
with:
  style: orbit
  theme: aurora
  coding-style: manual
  vibe-languages: "TypeScript,JavaScript"
  classic-languages: "C#,Python"
```

规则：

- 同一种语言不能同时出现在两个列表；
- 未出现在列表中的语言归入 `unclassified`，不能自动当作 `classic`；
- 配置只改变统计分组和展示，不改变原始语言字节数；
- 输出数据中标记 `classificationSource: user-declared`；
- 只有启用分组的卡片才显示简短说明，例如 `Grouped by the profile owner's choices`。

### 展示方式

- `bars`：Vibe / Classic / Unclassified 三个区块，各自列出语言；
- `orbit`：每个分组是一条独立轨道，轨道内按语言颜色切分；
- `constellation`：每个分组形成一个独立星团；
- 卡片同时显示各分组占全部已统计代码的比例，语言百分比仍以全部代码为分母，避免两个不同口径混淆。

### 已知限制

首版按“整种语言”标记，因此无法表达“这个 TypeScript 仓库是 vibe，另一个 TypeScript 仓库是传统编程”。如果真实用户频繁遇到这种情况，再增加按仓库覆盖的配置；首版不为尚未验证的复杂度提前设计完整规则系统。

## 6. 当前产品顺序

当前进度（2026-08-12）：第 1、2 项已完成；第 3 项中的六套主题与预览画廊已完成，“使用 AI 协助安装”尚未实现。`v0.2.0` 交付三种布局、六套主题和可直接比较的示例，视觉差异化文案的发布门槛已满足。Marketplace 上架前还需完成安装体验与发布准备。

1. 将现有统计核心迁入独立仓库并包装成可复用 Action；
2. 实现 `orbit`、`constellation` 和重制的 `bars`；
3. 实现主题、预览画廊和“使用 AI 协助安装”；
4. 发布免费 GitHub Action 到 Marketplace；
5. 增加默认关闭的用户自报编程方式分组；
6. 从启用日起积累历史快照，再实现 timeline；
7. 暂不开发任何 AI 代码检测功能。

## 7. 远期视觉实验（不属于当前产品承诺）

在语言构成图和 Action 安装体验稳定之后，可以探索比统计图更具叙事性和传播性的独立输出，例如：

- 根据语言分布生成一个动物、抽象生物或开发者图腾；
- 用主要语言决定主体结构，用语言颜色和占比决定配色、纹理或配件；
- 根据长期语言变化生成不同阶段的形态或年度版本；
- 输出适合社交媒体分享的海报，同时保留一张准确的语言构成图作为数据依据。

这类功能应作为单独的 `art` / `mascot` 渲染器，而不是把现有统计卡描述得比实际更丰富。基本约束：

- 当前 README 和 Marketplace 文案不预告尚未实现的动物、角色或故事化内容；
- 相同数据与配置应产生稳定、可复现的结果，不做无意义的随机抽卡；
- 艺术图不能替代精确数据图，也不能暗示对性格、能力或编程水平的判断；
- 只有核心 Action、三种基础布局和安装体验稳定，并确认用户确实需要后，才进入原型阶段。
